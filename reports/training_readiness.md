顯存數字是 `torch.cuda.max_memory_allocated()`，不包含其他程式、驅動及所有保留快取；本輪沒有出現顯存不足。Loss 不等同回答正確率。

單步測試確認權重確實更新，重新載入後前向結果為有限值，才允許完整一輪。完整 adapter 也已由新的評估程序重新載入並產生回答。

環境版本：PyTorch `2.12.1+cu130`、Unsloth `2026.9.7`、Transformers `5.5.0`、TRL `0.24.0`、datasets `4.3.0`、PEFT `0.21.0`。`config/requirements-windows.lock.txt` 保存完整版本；`pip check` 通過。

本輪修正的實際相容性問題：

1. Unsloth 的 PyTorch 版本上限，需要相容的 CUDA 套件組合。
2. 量化模型附帶的模板與官方 Instruct 模板不同；統一採用已保存的官方 Instruct 模板。
3. 預先產生 token 與 assistant 遮罩，避開舊版 datasets 不支援的混合 JSON API。
4. 單步測試停用暖身，確認權重有變動；Transformers 的舊 `warmup_ratio` 參數會覆寫 `warmup_steps`，因此明確停用舊參數並檢查實際暖身步數。

## 回答比較：尚未通過

兩個模型使用相同提示、工具、五題驗證題與生成設定（不抽樣、最多 256 新 tokens）。這是固定小樣本探測，不是正式準確率。

| 檢查 | 原模型 | 本輪 adapter |
| --- | --- | --- |
| 四題應查班：完整工具名稱與參數匹配 | 0／4 | 0／4 |
| 一題目的地不明：不擅自呼叫工具 | 1／1 | 1／1 |
| 合計工具行為匹配 | 1／5 | 1／5 |

人工檢查最終 adapter 回答發現：

- `002`：錯說 A9 可以搭直達車，並重複詢問系統已有的時間。
- `003`：未呼叫工具就聲稱有直達車，也承諾查詢未提供的即時資料。
- `004`：捏造 T10／T01 站碼，輸出重複文字，工具 JSON 在生成上限處未完成。
- `V001`：捏造 S1／H2 站碼；工具正確回傳 `invalid_station`，模型卻把錯誤站碼繼續寫進答案。
- `V004`：能針對「市中心」追問明確目的站。

因此不能將「訓練完成」當成「查班可靠」。這輪沒有顯示工具行為匹配率改善。保留完整輸出：`outputs/eval/base.json`、`outputs/eval/adapter.json`。
